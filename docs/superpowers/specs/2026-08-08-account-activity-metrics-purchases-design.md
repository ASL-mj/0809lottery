# 多账号活动指标与购买操作设计

## 目标

在现有单页多账号工作台中，为每个账号独立展示当天活动状态，并提供购买一次抽奖和购买今日抽奖通行证的安全操作。继续复用服务端保存的认证状态，不要求浏览器重复登录，不增加跨账号统计或批量操作。

## 已核对的上游行为

设计依据 `https://www.0809.one/activity` 在 2026-08-08 发布的真实页面、前端资源和用户截图：

- 活动状态来自 `GET /lottery/api/dashboard`。
- 消耗激励共五档，当前页面门槛为 25、50、100、200、400 额度。
- 幸运积分上限为 300。
- `POST /lottery/api/draw-purchases` 每次购买 1 次当日有效抽奖机会。
- `POST /lottery/api/draw-limit/unlock` 解锁当天全部有效抽奖次数。
- 当前页面显示购买 1 抽需要 10 额度，今日通行证需要 30 额度；实现必须使用 dashboard 实时返回价格，不把价格作为固定业务常量展示或扣费。
- 所有金额在工作台统一换算并显示为 `$`。

## 页面布局

采用已确认的 A 方案。每张账号卡片在现有订阅和抽奖次数信息下增加三指标状态带：

1. 今日消耗：当天实际请求消耗额度的美元值。
2. 消耗激励：显示已完成档数与总档数，例如 `0 / 5 档`。
3. 幸运积分：显示当前积分与上限，例如 `4 / 300`。

状态带下方增加辅助信息：

- 距离下一档还差的美元额度；全部五档完成后显示“今日五档已达成”。
- 今日累计加抽次数。

购买区与签到、领取次数、手动抽奖、刷新次数、核对结果等日常操作分离：

- 次要按钮：`购买 1 抽 · $实际价格`。
- 主要按钮：`购买通行证 · $实际价格`。

桌面端两个购买按钮并排。手机端上下排列。账号名继续允许任意位置换行，新增指标和按钮不得造成横向滚动。

## 服务端数据模型

服务端从 dashboard 读取并向页面返回经过整理的字段，不透传上游原始响应：

- `today_spend_usd`
- `spend_tier_reached`
- `spend_tier_total`
- `next_spend_threshold_usd`
- `next_spend_remaining_usd`
- `spend_bonus_draws`
- `lucky_points`
- `lucky_max_points`
- `draw_purchase_cost_usd`
- `purchased_today`
- `purchase_pending`
- `purchase_unknown`
- `pass_unlock_cost_usd`
- `pass_unlocked`
- `day_key`
- `queried_at`

原始额度通过现有平台状态配置换算为美元。若换算配置不可用，该账号活动状态返回安全错误，不用原生额度冒充美元。

活动状态作为独立快照保存。账号列表初次加载可显示最近快照；用户点击刷新或完成购买后查询真实 dashboard 并更新快照。

## 认证与敏感信息边界

所有上游请求在服务端完成：

- 优先复用已保存的 Lottery Token。
- Token 无效或上游返回 401/403 时，沿用现有自动登录和 bridge 逻辑刷新 Token，保存后重试当前读取或购买操作一次。
- 浏览器响应、日志、错误信息和测试输出不得包含密码、Cookie、父级访问令牌、Lottery Token 或完整上游响应。
- 页面不得提供查看、复制、导入或导出认证数据的功能。

## 购买流程

### 购买 1 抽

1. 页面读取当前账号活动状态和实际价格。
2. 用户点击按钮，确认框显示账号、商品、美元价格和北京时间当日有效期。
3. 用户确认后调用工作台服务端购买接口。
4. 服务端为当前账号和本次操作生成独立幂等键，调用 `POST /lottery/api/draw-purchases`。
5. 无论上游直接返回成功、处理中或结果不明确，服务端都重新查询 dashboard 核对购买状态。
6. 成功时更新活动状态与抽奖次数快照，并返回购买内容、扣除金额和当前剩余次数。

### 购买今日通行证

1. 页面读取通行证价格和解锁状态。
2. 已解锁时按钮显示“今日通行证已购买”并禁用。
3. 未解锁时确认框显示账号、美元价格和当日有效期。
4. 用户确认后，服务端使用独立幂等键调用 `POST /lottery/api/draw-limit/unlock`。
5. 服务端重新查询 dashboard；只有 dashboard 显示已解锁，页面才反馈购买成功。

### 并发与重复扣款保护

- 同一账号同类购买在进行中时互斥。
- 页面提交后立即禁用对应按钮。
- 上游返回处理中或网络超时造成结果不明确时，保留同一幂等键并进入“待核对”状态，不允许再次购买。
- 只有 dashboard 明确显示成功，或明确返回未扣款的可重试失败，才能结束待核对状态。
- 购买 1 抽与购买通行证使用不同的操作类型和幂等键空间。

## 页面反馈

每个账号继续使用局部状态区反馈，不创建全局统计：

- 成功：显示商品、扣除的美元额度、当前剩余抽奖次数或通行证状态。
- 额度不足：明确显示购买失败，不自动重复请求。
- 登录状态失效：服务端自动刷新认证并重试一次；仍失败时显示重新认证失败。
- 处理中：显示正在核对，禁用同类购买按钮。
- 结果不明确：显示“购买结果待确认，请刷新状态核对”，禁止重复扣款。
- 其他错误：显示经过清理的错误信息，不暴露认证数据或内部幂等键。

## 不在范围内

- 跨账号消费、积分或购买统计。
- 批量购买、自动购买或定时购买。
- 修改消费激励门槛、幸运积分规则或上游价格。
- 购买外部充值商品、兑换码或其他活动权益。
- 在浏览器中保存登录密码、Cookie 或 Token。

## 验证要求

### 服务端

- dashboard 新旧响应结构均能解析活动字段。
- 今日消耗和价格正确换算为美元。
- 五档完成数、下一档和差额计算正确，包括零档和全部完成。
- 幸运积分与上限正确显示。
- 两类购买使用独立幂等键，并在重复点击时只产生一次上游副作用。
- 401/403 时刷新认证后只重试一次。
- 成功、额度不足、处理中、超时和结果不明确均有回归测试。
- API 和快照不包含密码、Cookie、Token、幂等键或未清理的上游响应。

### 页面

- 初始快照、刷新成功、刷新失败和无数据状态均可读。
- 确认框完整显示账号、商品、价格和当日有效期。
- 请求期间按钮禁用，反馈后焦点回到当前账号状态区。
- 通行证已购买时按钮禁用并显示正确文案。
- 1440px 桌面端和 390px 手机端无横向溢出，长账号名不挤压按钮。

## 完成标准

- 五个账号均可独立查询和显示今日消耗、消费激励进度及幸运积分。
- 两个购买按钮均通过确认框、幂等保护和 dashboard 核对完成真实操作。
- 原有签到、订阅、每日领取、手动抽奖、刷新次数和核对结果行为保持不变。
- 全量 Go 测试、竞态检测、静态检查、构建和前端脚本语法检查通过。
