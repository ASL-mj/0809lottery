# 0809 签到 Token 门槛设计

## 目标

将 0809 签到资格的本地触发规则统一为：账号在北京时间当日累计消耗的 `total_tokens` 达到 `1,000,000` 后，才能发起签到。该门槛是 Token 数量，不是美元额度，也不使用原生额度或额度换算结果。

本次同时调整自动签到：任务触发时未达到门槛则延后 30 分钟重试；达到门槛后执行签到；不得跨北京时间零点重试。

## 已确认的口径

- 数据来源：认证账号调用 `/api/rankings/users?period=today` 返回的当前用户 `total_tokens`。
- 门槛常量：`1_000_000` Token，边界值包含等于，即 `total_tokens >= 1_000_000`。
- 日界：`Asia/Shanghai` 的自然日，与现有 `Runner.today()` 和自动任务计划日期一致。
- 查询方式：每次手动签到或自动签到实际尝试前都实时读取当日 Token；不得以卡片缓存、历史快照或美元额度替代。
- 平台资格接口：Token 门槛满足后仍调用现有 `/api/user/checkin/eligibility` 作为平台侧最终保护，但其 `remaining`、`required` 和额度换算结果不再影响本地门槛判断或用户提示。

## 方案

### 统一资格检查

在 `Runner.Checkin` 的副作用开始前增加一个单一的 Token 门槛检查：

1. 复用当前有效父访问令牌获取 `RankingsUsers(..., RankingPeriodToday)`。
2. 从 `current_user` 或同一用户 ID 的记录读取 `total_tokens`。
3. 若请求返回 401/403，沿用现有父令牌刷新一次后重试；不触发密码登录。
4. 若低于门槛，保持签到 Action 为可重试、未开始副作用状态，返回清晰的 Token 进度信息，例如 `今日 Token 685K / 1M，距签到还差 315K Token`。
5. 仅在达到门槛后再调用现有平台资格接口；平台明确拒绝时沿用现有幂等、错误分类和记录逻辑。

手动签到和 `CheckinScheduled` 都通过 `Runner.Checkin`，所以共享同一判断，不引入第二套业务规则。

### 自动签到延后

现有 `AutoDrawScheduler` 已为签到计划持久化 `PlannedAt`、状态和备注，并在未满足条件时重试。将延后窗口从 1 小时改为 30 分钟，并把触发原因从“活跃度/额度不足”改为 Token 进度。

- 低于 `1M`：不调用 `POST /api/user/checkin`；将当前计划保持 `pending`，`PlannedAt = now + 30m`，备注和运行日志记录当前 Token、门槛和下一次时间。
- 达到 `1M`：下一次执行计划时继续现有签到流程。
- 下一次时间若不属于计划所在的北京时间日期：计划标记为 `skipped`，原因说明“当日未达到 1M Token，次日按原计划重新判断”。
- 认证失效、账号停用、平台错误、已签到和未知副作用结果继续遵循既有终态、重试和脱敏日志规则；只有“Token 未达门槛”走 30 分钟延后。

## UI 与 API

- 账号卡片的签到状态区域展示 Token 门槛进度和剩余 Token。显示复用既有 `K/M/B` 格式化函数。
- 进度仅来自当前日的 Token 快照或刚完成的签到资格查询；无当天数据时显示“签到条件：当日 Token 待查询”，不得用旧日期的数据。
- 现有接口协议保持兼容。签到响应和自动任务状态中增加或复用脱敏的 Token 进度文案，不暴露令牌、Cookie 或原生额度。
- `POST /api/accounts/{id}/token-usage` 仍保存 UI 查询快照；签到资格检查获得的当日 Token 可更新同一 `token-usage` 快照，避免页面在后续展示过期值。

## 测试与验收

新增或更新回归测试，至少覆盖：

1. `999,999` Token 时手动签到不发送签到请求，Action 可重试且消息包含 Token 差额。
2. `1,000,000` Token 时发送签到请求并可完成签到。
3. Token 查询遇到 401/403 时只刷新父令牌一次，不触发密码登录。
4. 自动签到低于门槛时计划延后恰好 30 分钟，保持 pending，并写入脱敏运行日志。
5. 最后一次延后会跨北京时间零点时，当日计划跳过，次日计划仍可按原任务配置生成。
6. 平台资格接口在已达 Token 门槛后拒绝时，不被本地规则绕过。
7. 前端和 API 不显示美元额度作为签到门槛，也不输出认证凭据。

验收以 `go test ./... -count=1`、`go vet ./...`、`make build`、前端 JavaScript 语法检查和 `git diff --check` 为准。真实账号验证只在本地启动且用户授权的环境中进行，不自动登录或创建新平台会话。
